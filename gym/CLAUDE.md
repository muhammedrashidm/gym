# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter mobile app ("Kinetic") for a gym platform, serving two roles from one codebase: **member** (workout/recovery tracking) and **staff/trainer** (client management, live session tracking). This `gym/` directory is a subfolder of a larger monorepo (sibling `owner/` is a React web app, `server/` is the NestJS backend) — this file covers only the Flutter app.

## Commands

Run all commands from this `gym/` directory.

```bash
flutter pub get                          # install dependencies
flutter run --flavor dev -t lib/main_dev.dart        # run dev flavor (default local API: 192.168.0.11:3000)
flutter run --flavor staging -t lib/main_staging.dart
flutter run --flavor prod -t lib/main_prod.dart

dart run build_runner build --delete-conflicting-outputs   # regenerate *.g.dart, *.freezed.dart, injection.config.dart
dart run build_runner watch --delete-conflicting-outputs   # regenerate on save

flutter analyze                          # static analysis (flutter_lints)
flutter test                             # run all tests
flutter test test/widget_test.dart       # run a single test file
```

There are three flavors (dev/staging/prod), each with its own entrypoint (`lib/main_dev.dart`, `lib/main_staging.dart`, `lib/main_prod.dart`) and matching Android `productFlavors` / config in `lib/core/config/app_config.dart` (`AppConfig.dev/.staging/.prod`). Always pass `--flavor` and `-t` together — they must match.

Code generation is required after editing anything annotated `@freezed`, `@JsonSerializable`, `@injectable`/`@singleton`/`@Injectable(as:)`. Generated files (`*.freezed.dart`, `*.g.dart`, `injection.config.dart`) are committed — regenerate and commit them alongside source changes, don't hand-edit them.

## Architecture

Clean Architecture, feature-first, under `lib/features/<feature>/{data,domain,presentation}`. Features: `auth`, `member`, `profile`, `staff`, `workout` (plan authoring), `workout_session` (live execution/logging). Each feature's `domain` layer owns entities/repositories/usecases and must not depend on `data` or `presentation`.

**Request flow**: `presentation/cubit` → `Mediator.sendCommand()` → `domain/usecases` (`ICommand`/`ICommandHandler` pairs, CQRS-style via `dart_mediatr`) → `domain/repositories` (interface) → `data/repositories` (`@Injectable(as: X)` impl) → `data/datasources` → `ApiClient` (Dio). Repositories return `Either<Failure, T>` (`dartz`); datasources throw, repositories catch `DioException` and map to `Failure` (`lib/core/error/failures.dart`: server/network/unauthorized/unknown).

**DI**: `get_it` + `injectable`. `lib/core/di/injection.dart` is hand-maintained: it registers a few externals (`AppConfig`, `FlutterSecureStorage`, `SharedPreferences`, notifications plugin) manually, then runs generated `getIt.init()` (`injection.config.dart`, regenerated by build_runner), then wires every `ICommandHandler` into the shared `Mediator` singleton by hand — **any new command/query handler must be added to this file's `configureDependencies()` registration list or the mediator will not dispatch it**, even though DI resolution alone would succeed.

**Routing**: `go_router` in `lib/core/router/app_router.dart`, route names/paths centralized in `app_routes.dart`. Single `RouterGuard` (`router_guard.dart`) does all auth/role redirect logic based on `AuthCubit` state (`AuthInitial/CheckingToken` → splash, `Unauthenticated/Error` → login, `Authenticated` → routes to member or staff `ShellRoute` based on `activeRole`, blocks cross-workspace navigation). Two `ShellRoute`s provide the member and staff bottom-nav shells; some routes (e.g. `clientSessionUpdate`) are deliberately root-level/pushed over the shell to hide the bottom nav during active logging.

**Auth**: `AuthCubit` (`lib/features/auth/presentation/cubit/auth_cubit.dart`) is the single source of truth for session state, decodes the JWT `roles` claim into `UserRole`s and resolves the active workspace role (persisted preference → member role by default → server `isCurrent` hint → first role). Access/refresh tokens live in `SecureStorage`. Token refresh is centralized in `TokenRefreshService` (single-flight — concurrent 401s await one in-flight refresh since the refresh token is single-use/rotating) and triggered by `AuthInterceptor`, which queues parallel requests during a refresh and retries them after. A forced logout only ever happens when the server explicitly rejects a refresh — never from a local/offline expiry check.

**Local-first workout sessions**: `workout_session` feature persists in-progress sessions to on-device `sqflite` (`lib/core/database/app_database.dart`) via `WorkoutSessionLocalDataSource` as the source of truth while a session is active, syncing to the server on completion. `SessionSyncService` (`lib/core/live_session/session_sync_service.dart`) is a singleton bootstrapped at app start that watches the same local draft streams to drive an ongoing Android notification — it never maintains separate state, only mirrors what the session cubits already write, to avoid drift.

**Models**: `freezed` for immutable domain entities/states, `json_serializable` for API (de)serialization, kept in `data/models` separate from `domain/entities` with explicit `toDomain()` mapping.
